## 1. Selected Use Case & Target Users
**Use Case:** A city-wide, cross-institutional resource-sharing network. 
**The Problem:** Under-resourced government schools, charities, and community groups often lack access to essential educational tools (labs, smart classrooms, transport). Meanwhile, better-funded institutions have these exact resources sitting idle. Traditional booking systems fail because they lack trust verification, safety protocols, and fair allocation mechanisms.
**Target Users:**
*   **Teachers (Seekers):** Educators looking for resources for their students.
*   **Institutions (Providers):** Colleges or trusts with idle assets (labs, buses, halls).
*   **Platform Admin:** The central authority verifying identities and resolving disputes.

## 2. Core Solution & Workflow
We built a trusted platform that handles the complete lifecycle of a shared resource:
1. **Verification:** Users register and upload official ID cards. The Admin manually verifies these documents before granting access.
2. **Discovery:** Providers list resources with photos, max capacity, rules, and assigned resource persons.
3. **Smart Allocation (Hybrid AI + Human):** When a Teacher requests a resource, our custom algorithm instantly calculates a **Priority Score** based on group size, lead time, and conflicts. The system flags this score and presents it to the Provider, who makes the final human-in-the-loop approval.
4. **Lifecycle Management:** Teachers must "Check-In" (with photo proof) and "Check-Out" (return with photo proof) to ensure accountability. 
5. **Fairness & Penalties:** The system caps active bookings per teacher (max 2) to prevent monopolization. Overdue returns are flagged red. Users can report damage incidents.
6. **Auditability:** Every single action (approval, check-in, rejection, incident) is logged in an immutable Audit Trail visible to the Admin.

## 3. Features Developed During the Hackathon
*   Role-Based Access Control (RBAC) with separate dashboards for Admin, Teacher, and Owner.
*   Automated Fairness Engine (Priority Scoring: `Group Size * 2 + Days in Advance`).
*   Supabase Auth & Row Level Security (RLS).
*   Photo documentation for ID verification and condition reporting.
*   Automated transactional emails (Brevo) for approvals, waitlists, and incidents.
*   Fully responsive, mobile-first UI using Tailwind CSS.
*   Overdue resource flagging and incident management.
*   Global Audit Log for administrative oversight.

## 4. Technology Stack & Architecture
*   **Frontend & API:** Next.js (App Router), React, Tailwind CSS.
*   **Database, Auth & Storage:** Supabase (PostgreSQL).
*   **Email Notifications:** Brevo API.
*   **Deployment:** Vercel.
*   *AI Tools:* We used AI assistance for code generation and debugging during the 48-hour build. The logic for the fair allocation is a custom mathematical algorithm built into the app.

## 5. Privacy, Security & Fairness Considerations
*   **Security:** Middleware protects all routes. Unverified users are locked out of the dashboards. RLS policies protect the database. Sensitive ID documents are stored in a separate Supabase bucket.
*   **Fairness:** First-Come-First-Serve is abolished. The Priority Score ensures that larger, well-planned educational trips take precedence over small, repetitive bookings. The 2-active-booking limit prevents hoarding.
*   **Trust:** Human oversight is maintained. The Admin must verify users, and the Owner must approve requests.

## 6. Known Limitations & Future Development
*   **Payments:** Transportation fuel costs are currently logged manually. Future iterations would integrate Stripe/Razorpay for seamless COD.
*   **Domain Verification:** The email system uses a verified personal sender. In production, this would be tied to the institution's official domain.
*   **Future:** Integration with Google Calendar, mobile app for quicker photo uploads, and AI-based ID document OCR.
